code rather than from plans, brought up to date on 30 October 2026 with the fixes merged that day (each status
names the files that carry it). Each item has a location, the expected behaviour, an effort (S: under a day,
M: days, L: weeks) and a risk if left (Low, Medium, High). Items marked **Handed over** were found during

inside the diligence package's own files.

| D-12 | Session JWT in `localStorage`. **Fixed (5 November 2026)**: the browser session is the httponly `mn_auth_token` cookie (SameSite=Lax, Path=/, Secure when the request came over TLS, so plain http still works) and nothing else; the page keeps no token. CSRF is a double-submit cookie: login sets a readable `mn_csrf` cookie holding a random value, the API client echoes it in `X-CSRF-Token` on every non-GET request, and `LocalAuthMiddleware` compares the two with `hmac.compare_digest` on every cookie-authenticated POST, PUT, PATCH and DELETE (403 on a mismatch or a missing half; sign-out is exempt, since forging it only signs the victim out). It was chosen because it needs no server-side state, no extra table and no new dependency, and an attacker page on another origin can neither read the cookie nor set one for this origin, so it cannot produce a matching header; SameSite=Lax already blocks cross-site cookie-bearing POSTs in current browsers and the token covers the rest. A request with an `Authorization: Bearer` header (API keys, SCIM, MCP, scripts, tests) is judged on the header alone and needs no CSRF token, because a browser never attaches that header on its own. Login still returns the token in the body for machine clients; the OIDC callback no longer puts it in the URL fragment (only `sso=1`). A browser that still holds an old `localStorage` token sends it once as a bearer header to `/api/v1/auth/me`, which answers by issuing the cookies; the page then deletes the key. An expired or revoked old token gets a 401 and the page lands on sign-in with the key removed. Sign-out clears both cookies and the marker; other tabs find out on their next request (401). `tests/test_session_cookie_csrf_pg.py`, `frontend/lib/api/__tests__`. Not covered: the CSRF check does not apply to a cookie-authenticated GET, by design, so no GET may change state. | `frontend/lib/api/auth.ts` (`TOKEN_KEY`, `localStorage.setItem`), `frontend/lib/api/client.ts` line 96, `frontend/context/auth-context.tsx` | move to the httponly cookie the API already sets, with a CSRF token for mutating requests | M | Medium |

## 2. What the architecture allows next

These follow from what is already built, not from a plan document.

- **More SAP sources without new plumbing.** A source is a connector (`sap/base.py`: `SAPConnector` or
  `CloudSAPConnector`), an extraction registry entry and YAML rules; the check engine, scoring, work
  ledger and UI are source-agnostic. SAP Datasphere, MDG staging tables or a non-SAP ERP are each a
  connector and a rule family.
- **Rules at catalogue scale.** 2,757 DDIC-derived rules already ship disabled; enabling them per tenant
  is a row in the rules table. `workers.tasks.fix_mining` proposes rules from stewards' repeated manual
  fixes (never auto-enabled). Growth is YAML and Python, reviewable and testable, not prompts.
- **Hosted or multi-business-unit operation.** The schema is multi-tenant with forced RLS on every tenant
  table, so a vendor-hosted offering or one deployment for several business units needs no schema change;
  the work is in tenant provisioning and per-tenant encryption keys for extracts.
- **Change data instead of full extracts.** `api/services/delta_extraction.py` and `record_hashes` exist;
  routine runs on deltas cut extraction time and storage.
- **Write-back as a product.** Approved fix batches leave as load files with four-eyes approval and an
  audit trail. Live BAPI write-back for material master, customer, business partner and vendor (through
  its business partner, where CVI links one; simulate then commit) is in the code behind a switch and not yet run against a live SAP system (DR-2); each further object is a verified BAPI parameter mapping and a sandbox
  test, not new plumbing.
- **Model independence.** Every number is deterministic and every model call is optional and logged, so
  the model provider can change (or be removed) without changing results; the risk in an acquisition is
  low because the product does not depend on a model to be correct.
- **Constraints to plan for.** The issue lifecycle on very large scopes (D-24), the licence worker for connected installs (a 14-day signed grace since PC-14), and Postgres as the only store for findings
  (a columnar store would be the next step past tens of millions of failing records).

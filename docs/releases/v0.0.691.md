# v0.0.691

Status: not yet tagged. This note covers ops batch B for `scripts/update.sh`: the updater now drains the worker before it touches anything, migrates once before the new release starts, checks disk before the backup and leaves a recovery file when it fails. Change the heading if the number differs.

Previous release with notes: v0.0.673.

## Summary

The update script could still kill or lose work in three ways: a task waiting in a queue started on the new worker against a half-migrated schema, a task started in the seconds between the busy check and the restart was killed, and the api, worker and beat all migrated at once as they came up. This batch closes those gaps and makes a failed update easier to recover by hand. The prod entry point and every flag stay the same.

## Features

- Queued work: the update now refuses when tasks are waiting on any queue the worker consumes, and names the queues and the count. `--force` still overrides it.
- Drain before the final check: before the backup the script stops beat and cancels the worker's consumers on each of its queues, then checks the worker again. If something started meanwhile it adds the consumers back, starts beat and refuses. Any later error also resumes the worker, so a refused or failed update never leaves the queues paused. `--force` skips the drain.
- Migrate before restart: the script stops worker and beat, runs `alembic upgrade head` once in a one-off container on the newly pinned image, and only then starts api, worker and beat. A failed migration rolls back without the new release ever serving.
- Recovery file: when an update fails after the backup, `backups/update-state` records the from and to tags, the backup path, the failed step and the exact restore command, and the script prints the next steps. A successful update removes the file. It holds no secrets.
- Disk check: before `pg_dump` the script checks that the filesystem holding `backups/` has at least 1.2 times the database size free, and refuses with both figures if not. Nothing is changed when it refuses.

## Fixes

- The health wait message now says 300s, matching the actual wait.
- Migrations 103, 135 and 139 build their indexes CONCURRENTLY. A build that fails leaves an INVALID index that `IF NOT EXISTS` then skips for ever. Each create is now preceded by `drop_invalid_index` (in `db/migration_lock.py`), which drops the index only when Postgres marks it invalid, so a re-run builds it for real.
- The forced update task's comment now points at the drain in `update.sh` instead of a known race.

## Docs and training

None.

## Database migrations

No new revision. Migrations 103, 135 and 139 changed only in how they re-run after a failed concurrent build; a database that already ran them is not affected. A new test (`tests/test_migration_concurrently_lint.py`) fails any migration that uses CONCURRENTLY without `IF NOT EXISTS` / `IF EXISTS` or without `drop_invalid_index` before a create.

## Configuration changes

None. No environment variable was added, renamed or removed.

## Deployment

Deploy the API and worker images. Run the update the usual way: `sudo -n /usr/bin/bash /opt/meridian/scripts/update.sh`. The update that installs this release syncs the new `update.sh` and re-executes it, so the new checks and order apply on that same run.

- To confirm (release owner): on the next prod update, check that the log shows the consumers cancelled, one migration run, then api, worker and beat started, and that the worker consumes its queues afterwards.

## Rollback

Run `sudo -n /usr/bin/bash /opt/meridian/scripts/update.sh --rollback`. Nothing stored changed, so no data step is needed.

## Known issues

- A drain refused on a busy worker means the update waits for the next window; use `--force` only when losing the running task is acceptable.

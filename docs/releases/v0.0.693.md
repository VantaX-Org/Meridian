# v0.0.693

Status: not yet tagged. This note covers the remaining edge-ops items from batches A, C, D and E: the system download lock now fails closed, a cancelled download stops reading, `/health` reports the scheduler and free disk, and backups can be copied off the host. Change the heading if the number differs.

Previous release with notes: v0.0.691.

## Summary

Most of these audit items were already closed by #713, #715, #717 and #723. This release closes the four gaps that were left. Two of them could let two downloads log on to one SAP system at once: a Redis outage let every run through the system lock, and a cancel freed the lock while a worker the revoke missed was still reading. The other two are about seeing trouble early (a stopped scheduler or a filling disk) and about keeping a backup somewhere other than the disk it protects.

## Features

- Off-host backup copy (#12): `scripts/backup.sh --copy-to DEST` (or `MERIDIAN_BACKUP_COPY_TO`) copies the finished bundle with rsync to `host:/path`, or to a local path such as a mounted share. `--install-timer` carries the option into the nightly schedule. If the copy fails the script exits 3 and keeps the local bundle. Nothing on the far side is deleted, so retention there is up to the target.
- Scheduler and disk on `/health` (#41): two new components that do not gate readiness. `beat` is up while the 5-minute health sample has run in the last 15 minutes, and degraded otherwise. `disk` is degraded when the filesystem at `MERIDIAN_HEALTH_DISK_PATH` (default `/`) has less than `MERIDIAN_DISK_WARN_GB` (default 10) free. Both show in the `degraded` list.

## Fixes

- The system lock fails closed (#17): when Redis cannot be reached the download is refused with "The download lock service (Redis) is unavailable; try again shortly" and the status `lock_unavailable`, instead of starting without a lock. With no broker configured at all (dev and tests) behaviour is unchanged. The per-version lock still fails open, because the system lock is what stops concurrent RFC logons.
- A cancelled download stops reading (#29): the extraction checks its job at every progress report and stops with status `cancelled` once the job is cancelled. Before this, a worker that the revoke did not reach kept reading after the cancel had freed the system lock, so a new download could start beside it.

## Already done before this release

- #15, #16, #19, #20, #22, #28 (locks released in `finally`, one-hour lock with refresh, cancel and reaper release the locks, orphan reaper): #723. After an OOM kill the redelivered copy exits as a duplicate and the reaper fails the job and frees both locks, so the run ends as a clean, retryable failure. A heartbeat takeover was not added because it would bring back the double logon the version lock prevents.
- #34, #35 (Redis appendonly with a volume, worker memory limit, grace period and healthcheck): #715.
- #13 (restore stops services, dumps first and drops with FORCE): #715.
- #38, #40 (pool pre-ping and recycle, tenant setting reset on checkin): #717 and earlier.

## Configuration changes

New, all optional: `MERIDIAN_BACKUP_COPY_TO`, `MERIDIAN_DISK_WARN_GB` (default 10), `MERIDIAN_HEALTH_DISK_PATH` (default `/`). The beat tick is stored in Redis under `meridian:beat:last_tick` with a one-day expiry.

## Deployment

Deploy the API and worker images the usual way. The `beat` component reads degraded for up to 5 minutes after the first deploy, until the first health sample runs. To add an off-host copy to an existing schedule, run `sudo bash scripts/backup.sh --install-timer --copy-to DEST` again.

## Known issues

- The disk check runs in the API container. It measures the host disk only when the container's root sits on it, which is the default Docker layout; set `MERIDIAN_HEALTH_DISK_PATH` to a mounted data path otherwise.

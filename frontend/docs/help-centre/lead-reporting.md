# Reporting up

Reporting in Meridian is choosing the honest number that answers the question, and saying what it does not cover. The pages already hold the figures; the work is framing them for people who decide things with them.

## The executive view and the board pack

The executive view is one page for leadership: the score and what caps it, readiness by wave, value at risk, and owners. Its first line is the verdict, so a reader who stops after thirty seconds has the accurate impression rather than the comfortable one.

The board pack is the shareable form of the same page, carrying the same deltas as the screen: what changed against the run before it, in the same lineage. A pack with no earlier run says nothing changed, which is a fact about your history rather than the data, and worth writing into the covering email yourself.

Presentation mode drops the navigation so any insight page fills a room's screen. Use it rather than screenshots: the run the figures come from is named on the page. Quote a score with its run, its date and its basis, which is the rules counted and the records they ran over. A percentage without its basis is not evidence.

## Owner scorecards and digests

The owners view shows score and open work per owner, lowest score first, each with the digest that owner receives. It answers who has to act, not which object is prettiest.

Send a digest from there, to one owner or to everyone with open items, and the same text arrives as a notification now; the standing schedule is unchanged.

A scorecard is only fair if ownership is real, so start with the [objects](/objects) list, where each object names an owner and a steward. Unassigned work shows as nobody yet, and it does not move: a third of a backlog with no name is a staffing finding, not a data finding. Keep assignments current when people change roles.

## Schedules, and the audit trail

A schedule generates a report on a cadence and delivers it to named users as a notification and an email attachment, or to configured channels. Email channels get the file; chat channels and webhooks get a link to the report library, because they carry no files. Recipients need the export right, or they are not sent it.

Set the schedule's time zone to the zone the readers live in. A Monday pack that lands at 02:00 local time is read late or not at all, and slots are computed in the zone you enter. A slot missed while the server was down is not back-filled, so check the schedule's history before treating a missing report as a data problem. Scheduled generation also needs the report export feature in your licence: where it is missing, a slot is skipped rather than sent, so confirm a new schedule by hand.

Auditors want evidence of control, not a score. Export the audit log for the period: it records every decision, approval and export with who, when and against which record, and an export holds a bounded number of rows, so narrow it by date. Fix batches read as four-eyes evidence, drafter and approver both named and timed, and exported files carry a fingerprint, so the file loaded can be matched to the file Meridian produced. The audit proves who decided, not that the value was right.

## Comparing runs for steering material

Steering committees ask whether the programme is on track, which is a comparison, not a snapshot. Pin a baseline run, usually the run after a clean-up or at programme start, and later comparisons read against it.

Tick two runs to compare them: which rules and records were fixed, which newly fail, and what each object's score did. Only rules that ran in both runs are compared, so a rule switched off cannot flatter the trend. Export the result as a proof of progress report or a comparison workbook, and put record counts beside the score: a rise built on a smaller extract will not survive a sceptical question. Where the pace is flat there is no projected finish and the page says so; report that honestly, since it is a better steering item than an invented date.

## Proven cost, and value at risk

These two money figures mean different things and must never be merged into one headline.

Proven cost is measured. It is money already posted in SAP on documents with a defective value, such as a payment sent twice. It happened, it is in the ledger, and it is reported per top-level process in your configured currency, never added across processes, because one record can sit in more than one flow.

Value at risk is priced, not measured. It is affected records multiplied by the value per record your tenant set for that feature, in its cost model. A feature nobody priced shows no value, so a blank is a configuration gap rather than a zero. Quote it with its formula, never as a saving.

In one line: proven cost is money you have already lost, value at risk is money you have agreed is exposed. Neither invites a third figure the tool did not compute.
